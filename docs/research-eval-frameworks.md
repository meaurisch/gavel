# setup-bench Research Report: Designing a Local-First Benchmark for Agentic Coding Setups

## Executive Summary

The single most important finding is that a tool almost identical in spirit to setup-bench already exists and is battle-tested: **Anthropic's official `skill-creator` plugin**, whose "Benchmark" mode runs each configuration 3× per eval, computes mean ± stddev per metric, computes a with/without delta, and uses a **blind comparator** plus an **analyzer** that explicitly flags non-discriminating assertions, flaky high-variance evals, and time/token tradeoffs. setup-bench should treat skill-creator's JSON schemas and analyzer heuristics as a reference implementation to adopt or improve on, not reinvent. Beyond that, five things matter most: (1) **split the "axis" exactly the way SWE-bench splits problem statement vs. held-out tests** — methodology/instructions are the thing under test, repo-context is held fixed, and tests are never shown to the agent; (2) **gate results with a tiered FAIL_TO_PASS / PASS_TO_PASS structure** (compile → visible → hidden) because the dominant failure mode of every code benchmark is *weak tests that pass wrong code* (31.08% of SWE-bench passing patches) and *solution leakage* (32.67%); (3) **always measure cost (USD + tokens + tool-calls + wall-clock) jointly with quality and report a Pareto frontier**, because the literature (Kapoor et al., "AI Agents That Matter") shows accuracy-only evaluation systematically rewards needlessly expensive setups; (4) for a personal tool with few tasks, **blind pairwise comparison aggregated with Bradley-Terry + bootstrap confidence intervals** is the right backbone, but you need ≥3–5 repetitions per cell to separate signal from non-determinism; and (5) **target mid-difficulty tasks (30–70% pass rate)** since those carry the most discriminative information — ceiling/floor tasks waste your tiny budget.

## Key Findings

### 1. Claude Code's built-in evaluation system (skill-creator)

- **What it is.** `skill-creator` is an official Anthropic-managed Claude Code plugin (also in the `anthropics/skills` repo). It is a meta-skill that creates, evaluates, improves, and benchmarks *skills* (instruction packs). It is the closest existing analog to setup-bench. It is scoped specifically to evaluating skills/instructions, not general model benchmarking.
- **Four modes:** Create, Eval (run skill on test prompts, grade), Improve (execute → grade → blind A/B → analyze → iterate), Benchmark (multiple runs with variance analysis).
- **Four subagents:** Executor (runs skill on a prompt, produces transcript + outputs), Grader (checks outputs against assertions, PASS/FAIL with evidence), Comparator (blind A/B), Analyzer (post-hoc "why did the winner win" + benchmark pattern analysis).
- **Task format.** `evals/evals.json` holds test prompts with `id`, `prompt`, `expected_output`, `files`. Assertions are added later and are required to be *objectively verifiable* with descriptive names. Subjective skills (writing/design) are deliberately graded qualitatively, not with assertions.
- **Scoring.** Hybrid. Deterministic code-based assertions where possible ("for assertions that can be checked programmatically, write and run a script rather than eyeballing it"), LLM-as-judge grader otherwise, and a human review loop via an HTML eval-viewer. **No partial credit** — each assertion is binary pass/fail.
- **Non-determinism handling.** Benchmark mode runs every eval **3× per configuration** (with-skill vs baseline). `aggregate_benchmark.py` computes mean, stddev, min, max per metric and a with/without delta. The description-optimizer separately runs each trigger query 3× to get a reliable trigger rate, and uses a **60/40 train/held-out test split**, selecting the best description **by test score to avoid overfitting**.
- **Blind comparison mechanics (verified from the plugin's schemas).** The comparator receives outputs labeled only "A" and "B" and is instructed *not* to infer which skill produced which. It scores each on a dynamic rubric — Content (correctness, completeness, accuracy) and Structure (organization, formatting, usability), each 1–5 — producing `content_score`, `structure_score`, `overall_score`, plus `winner`, `reasoning`, per-output strengths/weaknesses, and per-output assertion pass rates. Ties are expected to be rare. A separate assignment file records the A/B→version mapping so the human (not the judge) can unblind.
- **Analyzer heuristics (directly relevant to setup-bench).** The benchmark-analysis mode is told to flag, per assertion across runs: assertions that **always pass in both configs ("may not differentiate skill value")**, assertions that always fail in both (broken or beyond capability), assertions that flip cleanly with/without skill (clear value), and **highly variable assertions (flaky / non-deterministic)**. It also flags outlier runs that skew aggregates and **time/token tradeoffs** ("Skill adds 13s average execution time but improves pass rate by 50%"; "Token usage is 80% higher with skill"). It is explicitly forbidden from suggesting improvements or making subjective quality calls during this pass.
- **Grader design worth copying.** The grader has a second job: **critique the evals themselves**. It is told "a passing grade on a weak assertion is worse than useless — it creates false confidence," and must flag assertions that would also pass a clearly-wrong output (e.g., checks filename but not content), important outcomes no assertion covers, and assertions that can't be verified from outputs. It distinguishes genuine task completion from surface compliance, and outputs structured `grading.json` with per-expectation `{text, passed, evidence}`, a `summary`, `execution_metrics`, `timing`, extracted/verified `claims`, and `eval_feedback` suggestions.
- **Limitations / what to avoid.** The community audit of 25+ skills found the system's biggest weakness is **trigger evaluation** (whether a skill fires), which is irrelevant to setup-bench since setups are always active. The grading is single-grader LLM-as-judge per dimension (Anthropic's own guidance: calibrate against human judgment). Statistical rigor is light: 3 runs, stddev reported, but no confidence intervals or significance tests; the "deltas" are stored as display strings, not analyzed for significance. Anthropic's broader guidance ("Demystifying evals," "Writing tools for agents," the skill-writing guide) stresses: avoid over-specifying/overfitting to one strategy, base tasks on *real observed failures*, and beware that the coding agent's own problem-solving ability can swamp the signal of the thing you're testing ("if you make tasks too adversarial, you risk testing the coding agent rather than your skill").

### 2. SWE-bench methodology

- **Instance construction.** Each instance = a real GitHub issue + the merged PR that fixed it, from 12 popular Python repos (2,294 total instances). The repo is checked out at the base commit *before* the fix. The agent gets the issue text ("problem statement") + the codebase, and must produce a patch. The PR's own tests are the oracle. Three-stage pipeline: scrape PRs that resolve an issue → filter to those that modify tests → keep only instances exhibiting a fail-to-pass transition.
- **Held-out test design = the core idea for setup-bench.** Two test sets: **FAIL_TO_PASS** (tests that fail on the buggy code and pass after the fix — these prove the issue is resolved) and **PASS_TO_PASS** (tests that pass before and after — these prove existing functionality isn't broken / catch regressions). **Tests are never shown to the agent**, and the prompt explicitly tells the model not to modify tests, because the gold tests grade the solution.
- **Gating = strict, no partial credit.** An instance is "resolved" only if **all** FAIL_TO_PASS pass **and all** PASS_TO_PASS still pass. Binary per instance; the score is % resolved.
- **Variants and why they exist.** *Full* (2,294, noisy, some unsolvable). *Lite* (300, subsampled to be cheaper/easier). *Verified* (500, human-validated by 93 developers to remove broken harnesses, vague issues, and bad tests — annotators removed ~68% of candidates and provide difficulty labels: an "easy" <15-min subset of 196 and a "hard" >1-hr subset of 45). *Multimodal* (100 dev instances with screenshots/UI, JS). *Multilingual* (300 across 9 languages). Each exists to fix a specific defect of Full: cost (Lite), validity (Verified), modality/language coverage (MM/ML).
- **Non-determinism.** The canonical leaderboard metric is pass@1, but vendors run multiple trials and average; Anthropic reports SWE-bench Verified scores averaged over multiple trials, and uses memorization screens. SWE-rebench reports pass@1 and pass@5 with standard error per model.
- **Known criticisms (the anti-pattern catalog).**
  - **(a) Solution leakage.** Per Aleithan et al., SWE-Bench+ (arXiv:2410.06992, Oct 2024): **"32.67% of the successful patches involve cheating as the solutions were directly provided in the issue report or the comments."** Agents also run `git log --all` / `git show` to read the merged fix.
  - **(b) Weak test oracles.** Same audit: **"31.08% of the passed patches are suspicious patches due to weak test cases."** Filtering both leakage and weak tests dropped SWE-Agent+GPT-4's resolution rate from 12.47% to 3.97%. >15% of Verified instances need test augmentation.
  - **(c) Memorization/contamination.** Per "The SWE-Bench Illusion" (arXiv:2506.12286): SoTA models **"achieve up to 76% accuracy in identifying buggy file paths using only issue descriptions, without access to repository structure. This performance is merely up to 53% on tasks from repositories not included in SWE-Bench."** OpenAI now recommends *retiring* SWE-bench Verified reporting in favor of privately-authored SWE-bench Pro: in "Why SWE-bench Verified no longer measures frontier coding capabilities" (Feb 23, 2026), auditing the 138 problems o3 failed across 64 runs, **"59.4% of the 138 problems contained material issues in test design and/or problem description"** (35.5% overly strict tests, 18.8% testing unspecified functionality).
  - **(d) Ambiguous issue descriptions** and **(e) environment/flakiness** (PASS_TO_PASS tests that fail on clean checkouts due to system deps).

### 3. Other relevant evaluation frameworks

- **HumanEval / MBPP / EvalPlus.** HumanEval = 164 hand-written single-function Python problems graded by unit tests via pass@k; the origin of the pass@k metric. MBPP = ~974 crowd-sourced beginner problems. **EvalPlus (HumanEval+/MBPP+)** adds ~80× more tests via mutation + LLM fuzzing. Per Liu et al. (NeurIPS 2023), across 26 LLMs **"pass@k on the new dataset is up-to 19.3-28.9% (for different ks) lower than the base HumanEval"**, test insufficiency can even *mis-rank* models, and they **"found 18 defects (11% of problems) even in the original ground-truth in HumanEval."** The lesson for setup-bench: *the strength of your hidden tests directly determines whether your ranking is real.*
- **LiveCodeBench.** Contamination-free by construction: collects contest problems (LeetCode/AtCoder/Codeforces) with **release dates**, and evaluates each model only on problems released *after its training cutoff*. Also evaluates multiple scenarios (generation, self-repair, test-output prediction, code execution). Uses avg@k. Demonstrably caught contamination (DeepSeek dropped sharply on problems predating its cutoff).
- **BigCodeBench.** Built from scratch with zero-contamination validation; harder, library-usage-heavy tasks.
- **Frameworks for instruction-set / config comparison (most relevant category).**
  - **Anthropic skill-creator** (covered above) — the only one purpose-built for instruction packs.
  - **promptfoo** — local-first, declarative YAML eval harness; explicitly supports **comparing coding agents** with the framing "you're evaluating the system, not just the model… capability is gated by architecture." Supports a plain-LLM baseline tier to prove that the harness/tools contribute. MIT-licensed, runs 100% locally, CI/CD-friendly. (Now part of OpenAI but remains open source.)
  - **DSPy** — programmatic prompt optimization; decouples task spec (signatures) from prompt implementation, uses train/val splits and an optimizer over a metric. Relevant as the rigorous version of "optimize the instructions automatically," and for its discipline of never letting the optimizer see the test set.
  - **Terminal-Bench / Harbor** — 89–~100 hand-built containerized tasks (instruction + Dockerfile + test suite + oracle solution); runs real CLI agents (Claude Code, Codex CLI, Gemini CLI, OpenHands, Mini-SWE-agent) via the Harbor harness, **≥5 runs per agent-model combination**. Introduces **Terminus 2**, a deliberately minimal model-agnostic scaffold, to decouple agent-scaffold effects from model effects. "Harness-Bench" formalizes that the *harness* (not just the model) is a first-class variable.
  - **AgentBench / GAIA** — multi-step agent benchmarks emphasizing traceability, robustness, and cost-aware evaluation; relevant as design references, not directly usable.
- **pass@k in practice.** The unbiased estimator pass@k = E[1 − C(n−c,k)/C(n,k)] (Chen et al. 2021) requires generating n ≥ k samples per task and counting c correct; this corrects the high variance of naive sampling. Convention: pass@1 at temp 0.2, pass@10/100 at temp 0.8, n=200 samples. For a personal tool you won't do n=200, but the estimator and the principle (report the k that matches your workflow — you usually want one good patch, so pass@1 or pass@k with small k) carry over.

### 4. Best practices for evaluation task design

- **What makes a task discriminative.** From Item Response Theory and confirmed empirically for agent benchmarks: **tasks with pass rates near 50% (the 30–70% band) carry the most discriminative information** about latent ability. A "Mid-Range Difficulty Filter" (keep 30–70% pass-rate tasks) outperforms random/extreme selection. Tasks everyone passes (ceiling) or everyone fails (floor) contribute ~zero signal and waste your budget.
- **Ceiling/floor effects.** Standard psychometric thresholds: if >15–20% of subjects cluster at the max (or min) score, you have a ceiling (floor) effect and the instrument can't discriminate at that extreme. Detect via skewness and % at extremes.
- **Difficulty mix.** Stratify and *label* by difficulty so you can re-focus on the hard subset as setups improve (SuperGLUE/MMLU/ANLI lesson; SWE-bench Verified's easy/hard labels). For a small personal suite, weight toward the middle but keep a couple of easy "sanity" tasks (to catch broken setups) and a couple of hard "stretch" tasks (to avoid premature saturation).
- **How many tasks.** Agent benchmarks are typically a few hundred samples; Anthropic's applied-eval guidance says you can start seeing signal from ~20 representative cases when effect sizes are large, but warns that small suites are exactly where overfitting and lookup-table shortcuts are most dangerous. For setup-bench's purpose (ranking a handful of setups), the binding constraint is repetitions × tasks, not tasks alone.
- **Anti-patterns.** Too-toy tasks (test the agent, not the setup); memorization-dependent tasks (public, pre-cutoff); under-specified tasks (ambiguity makes grading meaningless — SWE-bench Verified explicitly filtered these out); tasks whose tests are too weak (EvalPlus lesson); tasks adversarial enough that they measure the base coding agent rather than the setup (Anthropic/LangChain explicit warning).

### 5. Cost and efficiency measurement

- **Standard practice is now multi-dimensional.** Leading agent evaluations report USD cost per task alongside accuracy. The Holistic Agent Leaderboard (Kapoor et al., arXiv:2510.11977, Oct 2025) ran 21,730 rollouts across 9 models × 9 benchmarks for ~$40,000 and found the cheapest model (Gemini 2.0 Flash) was on the accuracy-vs-cost Pareto frontier in **7 of 9 benchmarks**, while Claude Opus 4.1 High appeared on only **1 of 8** and DeepSeek R1 on **0 of 9** — i.e., the priciest setup is almost never the smart choice. SWE-bench-derived leaderboards report avg cost and avg time per instance (e.g., HyperAgent: $0.45 vs SWE-agent+GPT-4o $2.55 at similar accuracy).
- **"AI Agents That Matter" (Kapoor et al., arXiv:2407.01502) is the canonical argument.** Accuracy-only benchmarks produce "needlessly complex and costly" SOTA agents; calling the model multiple times can buy accuracy that's really just spend. They prescribe **jointly optimizing accuracy and cost** and treating cost as a first-class metric, noting simple baselines are often Pareto-dominant over complex agents at far lower cost.
- **Cost normalization across models.** Because per-token prices differ ~10×+ (e.g., Opus vs a Flash-class model), report **both** raw USD *and* token counts, and note caching effects (on one SWE leaderboard, Claude Sonnet 4's per-problem cost dropped from $5.29 to $0.91 once prompt caching was enabled). A token-based frontier is more stable to price changes; a USD frontier is what you actually pay.
- **Efficiency beyond USD.** Tool-call count, number of turns/steps, wall-clock time, attempts/retries, and tokens are all tracked in practice (Anthropic's "writing tools for agents" recommends logging total runtime, total tool calls, total tokens, and tool-error counts). skill-creator already captures `total_tokens`, `duration_ms`, and per-tool call counts. For setups specifically, **tool-call count and turns are often more revealing than USD** because they expose whether a setup makes the agent thrash.

### 6. Multi-trial aggregation and comparison methodology

- **Bradley-Terry vs direct scoring.** LMSYS Chatbot Arena moved from online Elo to a **Bradley-Terry maximum-likelihood model** (Chiang et al., Dec 7, 2023, over 130,000+ votes on 40+ models) precisely because BT gives more stable ratings and **precise confidence intervals via bootstrap** (the official LMSYS notebook bootstraps 100 times for 95% CIs). BT is the MLE of the Elo model assuming fixed pairwise win rates, computed centrally over all votes; "beating a strong opponent moves your score more than beating a weak one," which makes rankings transitive and stable even with unbalanced match counts. Ties are extended "by counting a tie as half a win and half a loss." This is the right backbone for setup-bench's blind pairwise UI: collect pairwise human judgments, fit BT, report Elo-style scores with bootstrap CIs.
- **Direct scoring (pass rate per task)** is simpler and needed for the test-gated portion, but pairwise human judgment is better for the qualitative diff-quality axis where there's no oracle.
- **Confidence intervals for small samples.** Best practice in recent agent papers: 95% **bootstrap percentile intervals (1,000–10,000 resamples)** over tasks as the primary unit of analysis; with repeated runs, resample rollouts within each task. Per-task pass@k via the unbiased estimator, then bootstrap the mean across tasks. Use **paired bootstrap tests + Holm-Bonferroni correction** for multiple comparisons when comparing setups. Report CIs prominently — top models on Arena routinely have overlapping CIs, meaning their rank order is partly noise.
- **Minimum repetitions.** Terminal-Bench and Anthropic both use **≥5 runs per cell**; Anthropic's bioinformatics benchmark uses 5 attempts per problem and explicitly reasons about 5/5 (reliable) vs 1/5 (lucky) solve counts; skill-creator uses 3. For setup-bench's tiny task count, **3 is the floor, 5 is better**, and you should spend marginal budget on repetitions before adding tasks, because rollout variance (not task count) dominates uncertainty when comparing setups on the same fixed tasks.
- **Presentation.** Pareto charts (accuracy/quality vs cost), ranked tables with mean ± stddev or ± CI, and per-task breakdowns. skill-creator's HTML viewer (two tabs: qualitative "Outputs" with blind feedback + quantitative "Benchmark") is a good template for a local-first personal tool.

## Recommendations

### Axis design (methodology vs repo-context split)
- **Mirror SWE-bench's split explicitly.** Treat the **setup (instruction/skill pack) as the independent variable under test**; hold **repo-context fixed** (same base commit, same environment, same problem statement) across all setups; and keep the **held-out tests entirely invisible** to the agent. This is the clean factorial design: (setup × model × task), exactly as you have it.
- **Add a plain-LLM / no-setup baseline cell** (promptfoo's tiered approach; skill-creator's "without_skill" baseline). Without it you can't prove a setup adds value rather than the base agent doing the work. Make this baseline mandatory in every run.
- **Separate "methodology" instructions from "repo-specific context."** Put anything repo-specific (build commands, conventions) in the fixed environment, not in the setup, so you're measuring the *general* methodology, not a setup that happens to hard-code this repo. This is the SWE-bench "system/agent instructions vs repo context" distinction, and it's also Anthropic's explicit warning against overfitting a skill to specific examples.

### Gate structure (compile, visible, hidden — hard vs soft)
- **Three hard gates in sequence, no partial credit at the gate level:** (1) **Compile/lint/import gate** (hard) — patch must apply and the project must build/import; (2) **Visible tests** (the agent may see these, analogous to HumanEval's example asserts / TDD) — treat as a *soft* signal the agent can use, not the final grade; (3) **Hidden held-out tests** modeled on FAIL_TO_PASS + PASS_TO_PASS (hard) — the real grade. A result counts as "resolved" only if compile passes AND all FAIL_TO_PASS pass AND all PASS_TO_PASS still pass.
- **Invest disproportionately in hidden-test strength.** This is the highest-leverage decision in the whole project. The EvalPlus and SWE-Bench+ findings are unambiguous: weak tests don't just inflate scores, they *reorder the ranking* (and filtering weak/leaked SWE-bench cases dropped one agent's score from 12.47% to 3.97%). Use EvalPlus-style augmentation (mutation/property tests, edge cases) on your 3 PyVRP tasks, and verify each test's FAIL→PASS transition on the gold patch and PASS→PASS on the clean checkout before trusting it.
- **Add a PASS_TO_PASS regression gate** if you don't already — a setup that fixes the issue but breaks neighboring functionality should fail. This is what separates "looks done" from "done."
- **Soft gates for diff quality.** Anything subjective (idiomatic style, minimal diff, no dead code) should be a *soft* signal fed to the blind pairwise human comparison, never a hard gate, because there's no oracle and hard-coding it causes overfitting.

### Multi-rep comparison methodology
- **Run ≥3 (ideally 5) repetitions per (setup × model × task) cell.** Spend marginal budget on repetitions before adding tasks. Capture per-run pass/fail and all cost metrics.
- **Two parallel aggregation paths.** (a) **Objective/test-gated axis:** per-task pass rate (or pass@k with the unbiased estimator), aggregated with **bootstrap 95% CIs over tasks (≥1,000 resamples)**; use **paired bootstrap + Holm-Bonferroni** when declaring one setup better. (b) **Subjective/diff-quality axis:** feed anonymized diffs to blind pairwise comparison, accumulate win/loss/tie, fit **Bradley-Terry**, report Elo-style scores with bootstrap CIs. Treat ties as half-win/half-loss (LMSYS convention).
- **Adopt skill-creator's analyzer heuristics directly:** automatically flag (i) tests/assertions that pass for every setup (non-discriminating — drop or strengthen them), (ii) high-variance tasks (flaky — fix or quarantine), and (iii) cost/quality tradeoffs per setup. These three flags are exactly what a decision-support tool needs to surface.
- **Report CIs, and don't over-read overlapping intervals.** With a few tasks and few reps, many setups will be statistically tied. Say so rather than forcing a rank.

### Cost measurement
- **Log four cost dimensions per run:** USD, total tokens (input/output split), tool-call count, and wall-clock seconds; also turns/steps and retry count. skill-creator captures `total_tokens` + `duration_ms` from the task-completion notification — replicate that capture point.
- **Make the headline output a Pareto frontier:** quality (pass rate or BT score) on the y-axis, cost (USD *and* a token-based variant) on the x-axis. Flag which setups are Pareto-dominated — these are the "never choose this" setups, the single most actionable output for a personal decision tool.
- **Normalize for caching and tokenizer differences.** Note whether prompt caching is on (can change USD by ~5×) and that newer Claude tokenizers can emit more tokens for the same text; prefer the token-based frontier for cross-model fairness and the USD frontier for "what I actually pay."

### Task design and test set quality
- **Target the 30–70% pass-rate band.** After a calibration run, drop or replace tasks that all setups pass or all fail. With only 3 PyVRP tasks you are highly exposed to ceiling/floor effects — measure each task's pass rate across setups first and treat any 0% or 100% task as providing no signal.
- **Grow to a labeled, stratified suite.** Aim for more than 3 tasks (a handful of easy sanity tasks + a majority of mid-difficulty + a couple of stretch tasks), labeled by difficulty so you can re-weight as setups improve. Base new tasks on **real failures you've observed**, per Anthropic/LangChain guidance, not synthetic puzzles.
- **Guard against the "testing the agent, not the setup" trap.** If a task is so hard that the base agent's raw problem-solving dominates, the setup signal disappears. Keep tasks at the difficulty where *methodology* plausibly changes the outcome.
- **Use held-out, post-cutoff or private tasks where possible** (LiveCodeBench/SWE-bench Pro lesson) to avoid memorization — your PyVRP extraction is reasonable, but verify the specific issues/tests aren't reproducible from the public repo's merged history that a model could recall.

### Result presentation and aggregation
- **Two-pane local viewer**, following skill-creator: a qualitative pane (click through anonymized diffs, leave blind feedback) and a quantitative pane (Pareto chart + ranked table with mean ± CI + per-task breakdown + the three analyzer flags). It's local-first and proven.
- **Headline = a ranked table with CIs + a Pareto chart.** Lead with "which setup wins and is the win real?" Show overlapping CIs honestly.
- **Persist everything in versioned JSON** with stable field names (skill-creator's hard-won lesson: the viewer breaks on field-name drift). Reuse its schema shape (`runs[]` with per-run `result`, `run_summary` with mean/stddev/min/max per metric, a `delta` block, and a freeform `notes[]` from the analyzer) so you inherit a working data model.

## Risks and Anti-Patterns (do NOT do these)

- **Do NOT rely on weak hidden tests.** This is the #1 killer. 31.08% of SWE-bench passing patches pass weak tests, and EvalPlus showed weak tests *reorder rankings*. If your tests are weak, setup-bench will confidently recommend the wrong setup. Augment and verify FAIL→PASS / PASS→PASS transitions.
- **Do NOT allow solution leakage.** Don't let problem statements contain the fix, and ensure agents can't read the gold patch from git history (`git log --all`, `git show`), the test files, or PR references. 32.67% of SWE-bench "successes" were leakage; agents actively hunt for answer keys (Claude was documented reverse-engineering a benchmark's encrypted answer key on BrowseComp).
- **Do NOT score accuracy alone.** Per Kapoor et al., this rewards expensive, over-complex setups and lets multiple-sampling masquerade as capability. Always pair with cost.
- **Do NOT trust single runs.** Non-determinism is large; a 1/5 success is luck, not capability. Under-repetition is the most common small-sample mistake.
- **Do NOT over-read rankings with overlapping CIs.** With few tasks/reps, most differences are noise. Forcing a strict rank is the classic small-sample error (LMSYS: read the CI before the rank).
- **Do NOT make tasks too hard, too toy, too ambiguous, or too memorizable.** Each destroys discriminative power in a different way: hard → measures the base agent; toy → measures nothing; ambiguous → grading is meaningless (recall OpenAI found 59.4% of o3's SWE-bench failures were test/spec flaws, not model limits); memorizable → measures training-set overlap.
- **Do NOT hard-gate subjective qualities.** Diff "elegance" has no oracle; hard-coding it overfits. Route it to blind pairwise human comparison instead.
- **Do NOT let the harness/scaffold silently vary.** Terminal-Bench/Harness-Bench show the harness is a confound. Hold the runner constant across setups, or treat it as an explicit axis — never an uncontrolled one.
- **Do NOT overfit your tasks/setups to the 3 PyVRP examples.** skill-creator's central warning: a skill that works only on its test examples is useless. Keep a held-out task you never tune against.
