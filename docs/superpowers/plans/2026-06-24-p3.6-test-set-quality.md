# P3.6 — Test Set Quality Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give setup-bench the tooling and documentation to build *discriminative* evaluation tasks — a task-design guide, FAIL_TO_PASS/PASS_TO_PASS transition validation, a per-task calibration report, and a `difficulty` label on every task.

**Architecture:** Four mostly-independent deliverables. (1) Add a nullable `difficulty` field to `TaskSpec` + DB (with a backward-compatible column migration). (2) A read-only `scripts/calibrate_tasks.py` that reads `results.db` and reports per-task pass rates with difficulty bands. (3) New transition-validation functions in `scripts/validate_tasks.py` behind a `--validate-transitions` flag, reusing the existing worktree/install/test helpers. (4) `docs/task-design-guide.md` distilling the research findings, plus a README refresh.

**Tech Stack:** Python 3.12, Pydantic dataclasses, stdlib `sqlite3`/`argparse`, pytest. No new dependencies.

def _ensure_column(conn: sqlite3.Connection, table: str, column: str, decl: str) -> None:
    cols = {r["name"] for r in conn.execute(f"PRAGMA table_info({table})").fetchall()}
    if column not in cols:
        conn.execute(f"ALTER TABLE {table} ADD COLUMN {column} {decl}")


def init_schema(conn: sqlite3.Connection) -> None:
    conn.executescript(_SCHEMA)

    _ensure_column(conn, "task_spec", "visible_test_cmd", "TEXT")
    _ensure_column(conn, "task_spec", "difficulty", "TEXT")
    conn.commit()

"""
Per-task pass-rate calibration for setup-bench.

Reads a results database and reports each task's pass rate across all
methodologies and reps, with a difficulty band and ceiling/floor warnings.
This is a read-only analysis tool — it never modifies the database or tasks.

Difficulty bands (research §4, 30-70% discriminative window):
  easy   : pass rate > 70%   (sanity check; weak discrimination)
  medium : 30%-70%           (maximum discriminative power)
  hard   : pass rate < 30%   (may test the base agent, not the methodology)

Usage:
    python scripts/calibrate_tasks.py --db results.db
"""

import argparse
import sys
from pathlib import Path

PROJECT_ROOT = Path(__file__).resolve().parent.parent
sys.path.insert(0, str(PROJECT_ROOT))

from core.db import connect, get_gate_result, list_trials  # noqa: E402

CEILING = 0.70
FLOOR = 0.30


def task_pass_counts(conn) -> dict[str, tuple[int, int]]:
    """Return {task_id: (passed, total)} across all trials that have a gate result."""
    passed: dict[str, int] = {}
    total: dict[str, int] = {}
    for trial in list_trials(conn):
        gr = get_gate_result(conn, trial.id)
        if gr is None:
            continue
        total[trial.task_id] = total.get(trial.task_id, 0) + 1
        if gr.passed:
            passed[trial.task_id] = passed.get(trial.task_id, 0) + 1
    return {tid: (passed.get(tid, 0), total[tid]) for tid in total}


def classify(rate: float) -> tuple[str, str | None]:
    """Map a pass rate in [0, 1] to (difficulty_label, warning_or_None)."""
    if rate > CEILING:
        return "easy", "pass rate >70%, may not discriminate between methodologies"
    if rate < FLOOR:
        return "hard", "pass rate <30%, may be testing the base agent, not the methodology"
    return "medium", None


def format_report(stats: dict[str, tuple[int, int]]) -> str:
    lines = ["Task Pass Rates (across all methodologies and reps):"]
    recs: list[str] = []
    for task_id in sorted(stats):
        p, n = stats[task_id]
        rate = p / n if n else 0.0
        label, warning = classify(rate)
        if warning is None:
            note = f"[{label} - good discriminative power]"
        else:
            effect = "ceiling" if rate > CEILING else "floor"
            note = f"[WARNING: {effect} effect - {label}]"
        lines.append(f"  {task_id}:  {rate:.0%} ({p}/{n})   {note}")
        if warning is not None:
            recs.append(f"  - {task_id}: {warning}")
    if recs:
        lines.append("")
        lines.append("Recommendations:")
        lines.extend(recs)
    return "\n".join(lines)


def main() -> None:
    parser = argparse.ArgumentParser(
        description="Per-task pass-rate calibration (read-only)."
    )
    parser.add_argument(
        "--db", type=Path, default=Path("results.db"),
        help="Path to the results database (default: results.db).",
    )
    args = parser.parse_args()

    if not args.db.exists():
        print(f"error: database not found: {args.db}", file=sys.stderr)
        sys.exit(1)

    conn = connect(args.db)
    stats = task_pass_counts(conn)
    if not stats:
        print(f"No trials with gate results found in {args.db}.")
        sys.exit(0)
    print(format_report(stats))


if __name__ == "__main__":
    main()
```

def _run_build(wt_path: Path, build_cmd: str) -> tuple[bool, str]:
    """Run a build command in the worktree. Returns (succeeded, output)."""
    result = subprocess.run(
        build_cmd,
        cwd=str(wt_path),
        shell=True,
        capture_output=True,
        text=True,
        timeout=600,
        env=_build_env(),
    )
    return result.returncode == 0, result.stdout + result.stderr


def _validate_build_gate(task: dict) -> tuple[bool | None, str]:
    """build_cmd must succeed on the clean base commit. None if no build_cmd."""
    build_cmd = task.get("build_cmd")
    if not build_cmd or build_cmd == "null":
        return None, "no build_cmd"
    wt_path = None
    try:
        wt_path = _create_worktree(task["base_commit"])
        _patch_build_scripts_for_windows(wt_path)
        return _run_build(wt_path, build_cmd)
    finally:
        if wt_path and wt_path.exists():
            try:
                _destroy_worktree(wt_path)
            except Exception:
                log.warning("  Failed to destroy build-gate worktree %s", wt_path)


def _validate_fail_to_pass(task: dict) -> tuple[bool, str]:
    """Hidden tests must FAIL on the clean base commit (no changes).

    Returns (check_passed, output): check_passed is True when the tests FAIL,
    which proves they actually require the feature.
    """
    held_out_path = PROJECT_ROOT / task["held_out_tests_path"]
    wt_path = None
    try:
        wt_path = _create_worktree(task["base_commit"])
        if not _install_in_worktree(wt_path):
            return False, "install failed on clean base commit"
        created = _copy_held_out_tests(wt_path, held_out_path)
        try:
            tests_passed, output = _run_tests(wt_path, task["run_cmd"])
        finally:
            _cleanup_held_out_tests(created)
        return (not tests_passed), output
    finally:
        if wt_path and wt_path.exists():
            try:
                _destroy_worktree(wt_path)
            except Exception:
                log.warning("  Failed to destroy fail-to-pass worktree %s", wt_path)


def _validate_pass_to_pass_with_gold(task: dict) -> tuple[bool, str]:
    """Hidden tests must PASS after applying the reference (gold) diff.

    Returns (check_passed, output): check_passed is True when the tests PASS.
    """
    held_out_path = PROJECT_ROOT / task["held_out_tests_path"]
    diff_path = PROJECT_ROOT / task["reference_diff_path"]
    wt_path = None
    try:
        wt_path = _create_worktree(task["base_commit"])
        if not _apply_diff(wt_path, diff_path):
            return False, "failed to apply reference.diff"
        if not _install_in_worktree(wt_path):
            return False, "install failed with gold patch"
        created = _copy_held_out_tests(wt_path, held_out_path)
        try:
            tests_passed, output = _run_tests(wt_path, task["run_cmd"])
        finally:
            _cleanup_held_out_tests(created)
        return tests_passed, output
    finally:
        if wt_path and wt_path.exists():
            try:
                _destroy_worktree(wt_path)

def validate_transitions(task_dir: Path) -> dict:
    """Run build-gate, FAIL_TO_PASS, and PASS_TO_PASS(gold) checks for one task."""
    task = _load_task(task_dir)
    task_id = task["id"]
    result = {
        "task_id": task_id, "build_gate": None,
        "fail_to_pass": None, "pass_to_pass": None, "errors": [],
    }

    log.info("[%s] Build gate: build_cmd succeeds on clean base", task_id)
    try:
        bg, out = _validate_build_gate(task)
        result["build_gate"] = bg
        if bg is False:
            result["errors"].append(f"build gate: FAILED on clean base\n{out[-2000:]}")
            log.error("  Build gate FAILED:\n%s", out[-2000:])
    except Exception as exc:
        result["errors"].append(f"build gate: {exc}")
        log.exception("  Build gate error")

    log.info("[%s] FAIL_TO_PASS: hidden tests fail on clean base", task_id)
    try:
        ftp, out = _validate_fail_to_pass(task)
        result["fail_to_pass"] = ftp
        if not ftp:
            result["errors"].append(
                f"FAIL_TO_PASS: tests PASSED on clean base (tests too weak)\n{out[-2000:]}"
            )
            log.error("  FAIL_TO_PASS problem (tests passed on base):\n%s", out[-2000:])
    except Exception as exc:
        result["errors"].append(f"FAIL_TO_PASS: {exc}")
        log.exception("  FAIL_TO_PASS error")

    log.info("[%s] PASS_TO_PASS: hidden tests pass with gold patch", task_id)
    try:
        ptp, out = _validate_pass_to_pass_with_gold(task)
        result["pass_to_pass"] = ptp
        if not ptp:
            result["errors"].append(
                f"PASS_TO_PASS: tests FAILED with gold patch (tests or diff broken)\n{out[-2000:]}"
            )
            log.error("  PASS_TO_PASS problem (tests failed with gold):\n%s", out[-2000:])
    except Exception as exc:
        result["errors"].append(f"PASS_TO_PASS: {exc}")
        log.exception("  PASS_TO_PASS error")

    return result


def render_transitions_summary(all_results: list[dict]) -> tuple[str, bool]:
    """Render the transition-validation summary. Returns (text, all_ok)."""
    lines = ["", "=" * 60, "TRANSITION VALIDATION SUMMARY", "=" * 60]
    all_ok = True
    for r in all_results:
        bg = r["build_gate"]
        build = "PASS" if bg else ("SKIP" if bg is None else "FAIL")
        ftp = (
            "FAIL (correct)" if r["fail_to_pass"]
            else "PASS (too weak!)" if r["fail_to_pass"] is False
            else "SKIP"
        )
        ptp = (
            "PASS" if r["pass_to_pass"]
            else "FAIL (broken!)" if r["pass_to_pass"] is False
            else "SKIP"
        )
        ok = (bg is not False) and bool(r["fail_to_pass"]) and bool(r["pass_to_pass"])
        if not ok:
            all_ok = False
        status = "OK" if ok else "PROBLEM"
        lines.append(
            f"  {r['task_id']:12s}  build={build:5s}  F2P={ftp:16s}  P2P={ptp:14s}  [{status}]"
        )
        for err in r["errors"]:
            lines.append(f"    ERROR: {err.split(chr(10))[0]}")
    lines.append("=" * 60)
    lines.append(
        "All transitions validated successfully." if all_ok
        else "Some tasks have transition problems. See above for details."
    )
    return "\n".join(lines), all_ok
```

# Task Design Guide

How to build *discriminative* evaluation tasks for setup-bench. The core lesson
from the research (`docs/research-eval-frameworks.md` §4): **the strength of your
hidden tests directly determines whether your ranking is real.** Weak tests don't
just inflate scores — EvalPlus showed they *reorder rankings*, and SWE-Bench+
found 31% of "passing" patches passed only because the tests were weak.

## What makes a good task

- **Mid-difficulty (30–70% pass rate).** Tasks where some methodologies pass and
  others fail carry the most discriminative information. A task everyone passes,
  or nobody passes, contributes ~zero signal (Item Response Theory; confirmed
  empirically on agent benchmarks). Target the 30–70% band.
- **Based on real failures.** Tasks should come from real observed coding
  challenges, not synthetic puzzles. Anthropic and LangChain both warn that toy
  tasks measure the base agent, not the methodology.
- **Cross-layer scope.** Tasks spanning multiple files, languages, or
  abstractions (like the PyVRP tasks: C++ → pybind11 → Python) are more
  discriminative because they exercise how a methodology handles real complexity.
- **Clear specification.** The instruction must be unambiguous. OpenAI found
  59.4% of o3's SWE-bench failures were test/spec flaws, not model limits. A
  vague instruction tests the agent's ability to guess, not the methodology.

## Anti-patterns to avoid

- **Too easy (ceiling).** If >70–80% of methodologies pass, the task can't
  discriminate. Replace it or make it harder.
- **Too hard (floor).** If <20–30% pass, you're measuring the base agent's raw
  capability, not the methodology. Replace it or make it easier.
- **Memorizable.** Don't use public-repo tasks at commits before the model's
  training cutoff where the fix is obvious from commit history. PyVRP's approach
  (custom branch, features removed) is good — verify the fix isn't recallable.
- **Solution leakage.** The instruction must not contain the solution: no file
  paths, function signatures, or implementation hints that give the answer away,
  and agents must not be able to read the gold patch from `git log --all` /
  `git show` or the test files. 32.67% of SWE-bench "successes" were leakage.
- **Weak hidden tests.** A test that checks "does a file exist?" without verifying
  behavior is worse than useless — it gives false confidence. Every hidden test
  must verify actual behavior, not surface compliance.

## Test design: FAIL_TO_PASS and PASS_TO_PASS

From SWE-bench's methodology:

- **FAIL_TO_PASS** — tests that *fail on the base commit* (before any change) and
  *pass after a correct implementation*. These prove the feature was actually
  implemented. If they still fail, the agent didn't solve the task.
- **PASS_TO_PASS** — tests that *pass on the base commit* and *still pass after*
  the agent's change. These catch regressions: a methodology that "fixes" the
  problem by breaking something else should fail.

Grading is strict and binary (SWE-bench): an instance is resolved only if **all**
FAIL_TO_PASS pass **and all** PASS_TO_PASS still pass.

Document which held-out tests are which — a header comment in each test file, or a
`test_manifest.yaml` per task. setup-bench's current held-out tests are
FAIL_TO_PASS-style (they exercise the new feature); add PASS_TO_PASS regression
tests as the suite matures.

### Validating the transitions

`scripts/validate_tasks.py --validate-transitions` checks, per task:

- **build gate** — `build_cmd` succeeds on the clean base commit (the base
  environment isn't broken).
- **FAIL_TO_PASS** — hidden tests *fail* on the clean base commit. If they pass,
  the tests don't actually require the feature → too weak.
- **PASS_TO_PASS (gold)** — hidden tests *pass* after applying `reference.diff`.
  If they fail, either the tests or the reference diff are broken.

Run it in WSL (PyVRP requires Linux to build):

```bash
python scripts/validate_tasks.py --validate-transitions --verbose
```

## Difficulty labeling

After a calibration sweep, label each task in its `task.yaml` (`difficulty:`
field, values `easy` / `medium` / `hard`):

- `easy` — >70% pass rate (sanity check; catches broken setups)
- `medium` — 30–70% pass rate (maximum discriminative power)
- `hard` — <30% pass rate (stretch goal; avoids premature saturation as
  methodologies improve)

Keep a mix: a couple easy, a majority medium, a couple hard. Assign labels by
hand after reviewing calibration output — don't auto-assign.

Generate the calibration numbers with:

```bash
python scripts/calibrate_tasks.py --db results.db
```

It reports each task's pass rate across all methodologies and reps, bands it, and
flags ceiling (>70%) and floor (<30%) effects.

## How many tasks

For ranking a handful of methodologies the binding constraint is
`repetitions × tasks`, **not tasks alone**. Start with 3–5 tasks (current: 3) and
≥3 reps; spend marginal budget on reps before adding tasks. Aim for 10+ tasks
eventually to reduce per-task variance. With only 3 tasks you are highly exposed
to ceiling/floor effects — calibrate early and treat any 0% or 100% task as
providing no signal.
