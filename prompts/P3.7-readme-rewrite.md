### What it is

Lead with the framing: setup-bench is a local-first decision-support tool for
comparing agentic coding setups. It tells you which combination of methodology,
repo-context, model, and runner produces the best results for your tasks — and
at what cost.

Key points to cover:

**5-axis model:** Every axis is a comparison target.

| Axis | What it is | Example values |
|------|-----------|----------------|
| Task | The coding problem to solve | pyvrp-A, pyvrp-B, pyvrp-C |
| Methodology | Instruction/skill pack (the framework being tested) | baseline, superpowers, karpathy, ecc |
| Repo-Context | Repo-specific instructions (held fixed or varied per experiment) | none, pyvrp-instructions |
| Model | The LLM model | claude-sonnet-4-6, claude-opus-4-8 |
| Runner | The execution harness | claude-code, copilot-cli, manual |

Explain the separation: methodology is the general-purpose instruction framework;
repo-context is repo-specific knowledge. They're independent axes so you can test
each in isolation or in combination. Repo-contexts have task-affinity tags to
avoid nonsensical pairings.

**Three-tier gate scorecard:** Each trial gets a scorecard:
1. Compile gate — does the code build?
2. Visible test gate — do the tests the agent could see pass?
3. Hidden test gate — do the held-out tests pass? (the definitive quality metric)

Trials that pass the hidden gate enter blind pairwise grading.

**Blind pairwise grading with Bradley-Terry scores:** Anonymized diffs shown side
by side. Human judges pick A, B, or Tie. Judgments feed a Bradley-Terry model
that produces Elo-style scores with 95% bootstrap confidence intervals. Multi-rep
sampling ensures all repetitions contribute to comparisons.

**API-rate cost:** Cost computed from token counts × published API rates (not
self-reported). Reproducible and comparable across models. Wall-clock time
captured as a secondary metric.

**Analyzer flags:** Automatically surfaces non-discriminating tasks (all
methodologies pass or fail), flaky tasks (high variance across reps), and
cost/quality tradeoffs (expensive methodology with no quality gain).

**Isolated execution:** Every trial runs in a fresh git worktree. Held-out tests
live outside the worktree and are copied in only at gate time — test leakage is
impossible by construction.
