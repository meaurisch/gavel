## Context

setup-bench currently has 3 PyVRP tasks. The research report
(`docs/research-eval-frameworks.md` §4) delivers a strong message: *"The
strength of your hidden tests directly determines whether your ranking is real."*
Weak tests don't just inflate scores — they *reorder rankings*. EvalPlus found
that HumanEval's original tests gave up to 19–29% false-positive pass rates, and
SWE-Bench+ found 31% of passing patches were suspicious due to weak tests.

The research also says to target the 30–70% pass-rate band for discriminative
tasks, label tasks by difficulty, and base new tasks on real observed failures.

## What to build

### 1. Write `docs/task-design-guide.md`

A practical guide for creating discriminative evaluation tasks for setup-bench.
Structure:

#### What makes a good task

- **Mid-difficulty (30–70% pass rate):** Tasks where some methodologies pass and
  others fail carry the most discriminative information. A task that everyone
  passes or nobody passes contributes zero signal. (Research: Item Response
  Theory, confirmed empirically in agent benchmarks.)
- **Based on real failures:** Tasks should come from real observed coding
  challenges, not synthetic puzzles. Anthropic/LangChain explicitly warn against
  toy tasks that test the base agent, not the methodology.
- **Cross-layer scope:** Tasks that span multiple files, languages, or
  abstractions (like the PyVRP tasks: C++ → pybind11 → Python) are more
  discriminative because they exercise how a methodology handles complexity.
- **Clear specification:** The task instruction must be unambiguous. OpenAI found
  that 59.4% of o3's SWE-bench failures were test/spec flaws, not model limits.
  If your instruction is vague, you're testing the agent's ability to guess, not
  the methodology's quality.

#### Anti-patterns to avoid

- **Too easy (ceiling):** If >80% of methodologies pass, the task can't
  discriminate. Replace or make harder.
- **Too hard (floor):** If <20% pass, you're testing the base agent's raw
  capability, not the methodology. Replace or make easier.
- **Memorizable:** Don't use tasks from public repos at commits before the
  model's training cutoff if the fix is obvious from the commit history. PyVRP's
  approach (custom branch, features removed) is good.
- **Solution leakage:** The task instruction must not contain the solution. Don't
  include file paths, function signatures, or implementation hints that give away
  the answer. 32.67% of SWE-bench "successes" were leakage.
- **Weak hidden tests:** A test that checks "does a file exist?" without
  verifying its content is worse than useless — it gives false confidence. Every
  hidden test should verify actual behavior, not surface compliance.

#### Test design: FAIL_TO_PASS and PASS_TO_PASS

From SWE-bench's methodology:

- **FAIL_TO_PASS tests:** Tests that fail on the base commit (before the agent's
  changes) and should pass after a correct implementation. These prove the
  feature was actually implemented. If these still fail, the agent didn't solve
  the task.
- **PASS_TO_PASS tests:** Tests that pass on the base commit and should still
  pass after the agent's changes. These catch regressions — a methodology that
  "fixes" the problem by breaking something else should fail.

For each task, your held-out tests should include both categories. Document which
tests are FAIL_TO_PASS and which are PASS_TO_PASS (e.g., in a comment at the top
of each test file or in a `test_manifest.yaml`).

#### Difficulty labeling

After running a calibration sweep, label each task:
- `easy`: >70% pass rate across methodologies (sanity check — catches broken setups)
- `medium`: 30–70% pass rate (maximum discriminative power)
- `hard`: <30% pass rate (stretch goal — avoid premature saturation as
  methodologies improve)

Keep a mix: a couple easy, majority medium, a couple hard.

#### How many tasks

The research says: for ranking a handful of methodologies, the binding constraint
is `repetitions × tasks`, not tasks alone. Start with 3–5 tasks (current: 3) and
≥3 reps. Spend marginal budget on reps before adding tasks. Aim for 10+ tasks
eventually to reduce per-task variance.

### 4. Add calibration analysis — `scripts/calibrate_tasks.py` (new)

A script that reads `results.db` after a trial run and reports per-task stats:

```
$ python scripts/calibrate_tasks.py --db results.db

Task Pass Rates (across all methodologies and reps):
  pyvrp-A:  45% (9/20)   [medium - good discriminative power]
  pyvrp-B:  90% (18/20)  [WARNING: ceiling effect - consider making harder]
  pyvrp-C:  10% (2/20)   [WARNING: floor effect - consider making easier]

Recommendations:
  - pyvrp-B: pass rate >70%, may not discriminate between methodologies
  - pyvrp-C: pass rate <30%, may be testing the base agent, not the methodology
```

This is a read-only analysis tool — it doesn't modify the database or tasks.

## What NOT to do

- Don't actually augment the PyVRP hidden tests yet — that requires deep
  domain knowledge of PyVRP internals. The guide and validation tooling enable
  the user to do this incrementally.
- Don't auto-assign difficulty labels — the user reviews calibration output and
  labels manually.
- Don't implement automatic test generation (EvalPlus-style mutation) — that's
  a future enhancement if the task suite grows.
