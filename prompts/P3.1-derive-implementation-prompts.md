# P3.1 — Derive Implementation Prompts from Research

> **Run this in Claude Code.** This session reads the research report and
> produces the actual implementation prompts. The user will critically review
> every generated prompt before executing it.

## Context

setup-bench is a local-first benchmarking framework for comparing agentic coding
setups (instruction/skill packs) across harnesses, models, and tasks. After a
brainstorming session, we identified 6 areas for evolution. Rather than implement
from assumptions, we first ran a research investigation (P3.0). The research
report is at `docs/research-eval-frameworks.md`.

## Your Task

1. **Read the research report** at `docs/research-eval-frameworks.md` thoroughly.

2. **Read the design spec** at
   `docs/superpowers/specs/2026-06-24-research-driven-evolution-design.md`
   which documents our original intentions and open questions.

3. **Explore the codebase** to understand the current architecture. Key files:
   - `core/models.py` — data models (Trial, TaskSpec, SetupSpec, etc.)
   - `core/matrix.py` — trial expansion (Cartesian product)
   - `core/executor.py` — per-trial pipeline
   - `core/db.py` — SQLite schema and CRUD
   - `core/setup_loader.py`, `core/manifest.py` — setup/manifest system
   - `grading/gate.py` — held-out test gate
   - `grading/pairwise.py` — blind pair generation and diff anonymization
   - `ui/server.py` — FastAPI grading UI
   - `runners/claude_code.py` — Claude Code runner with cost extraction
   - `cost/claude_usage.py` — Claude usage parsing
   - `cli.py` — main CLI entry point

4. **For each of our 6 intended action points**, hold it against the research
   findings and decide:
   - **Confirm** — the research supports our intention as-is
   - **Refine** — the research suggests a better approach; explain what changes
   - **Redirect** — the research suggests we shouldn't do this, or should do
     something different entirely; explain why
   - **Defer** — the research suggests this isn't worth doing yet; explain what
     should come first

   The 6 action points are:

   a. **Axis refactor** — Split "setup" into "methodology" (instruction packs)
      and "repo-context" (repo-specific instructions) as independent axes. This
      makes the trial matrix 5-dimensional. The manifest system already handles
      per-harness file mappings, so repo-context would use the same pattern.
      Combinatorial explosion is managed via task-context affinity (a pyvrp
      context only applies to pyvrp tasks).

   b. **Gate system overhaul** — Three soft gates (compile, visible tests,
      hidden tests). All trials enter pairwise grading regardless of gate
      results. Gate scorecard shown alongside each diff. TaskSpec gets
      `build_cmd` and `visible_test_cmd` fields.

   c. **Multi-rep pairwise grading** — Random L-from-K×K sampling with balanced
      rep usage. Seeded RNG. Win/loss/tie tallies per matchup. No statistical
      significance numbers — this is a decision support tool, not a clinical
      trial.

   d. **Cost calculation refactor** — Compute USD from token counts × published
      API rates instead of self-reported cost. Pricing table in code. Tokens as
      secondary detail.

   e. **Test set quality** — Apply research findings to improve our task design.
      Update existing PyVRP tasks if needed. Create guidance for adding new
      tasks. Consider tooling to help validate task quality.

   f. **README rewrite** — Add "decision support tool" framing. Document the
      5-axis model, soft gates, blind pairwise grading, API-rate cost.

5. **Produce one prompt file per confirmed/refined action point.** Each prompt
   should be a self-contained instruction for a Claude Code session, following
   the style of existing prompts in the `prompts/` directory (see
   `P1.7-pairwise-ui.md` for the format). Save them as
   `prompts/P3.2-<topic>.md`, `prompts/P3.3-<topic>.md`, etc.

   Each prompt must include:
   - What to build/change and why
   - Which files to modify (be specific)
   - What the research says that informs this design
   - How to verify the changes work
   - Any decisions that were made and the reasoning

6. **Write a summary** explaining your decisions for each action point:
   what the research said, how it affected the original intention, and what the
   final prompt looks like. Save this as `docs/P3.1-decisions.md`.

## Constraints

- **Research is leading.** If the research contradicts our original intentions,
  follow the research. Explain clearly why and what changed.
- **Be specific in prompts.** Reference actual file paths, function names,
  model fields. The prompts will be executed by Claude Code agents that need
  precision.
- **Order the prompts by dependency.** Number them so they can be executed in
  sequence. Note which prompts depend on earlier ones.
- **Keep prompts focused.** Each prompt should be one coherent unit of work that
  can be completed in a single Claude Code session. If an action point is too
  large, split it into multiple prompts.
- **No premature implementation.** The prompts describe what to do — they don't
  contain the actual code. The executing agent writes the code.
