## Context

setup-bench currently has a 4-axis trial matrix: Task × Setup × Model × Runner
(with reps). "Setup" conflates two concerns: methodology packs (instruction/skill
frameworks like superpowers, karpathy, ecc) and repo-specific context (repo-
particular instructions and conventions).

The research report (`docs/research-eval-frameworks.md` §Axis design) says:
*"Separate methodology instructions from repo-specific context."* The user wants
**all axes to be comparison targets** — including the ability to compare different
repo-specific instructions independently.

The solution: split "setup" into two independent axes — **methodology** and
**repo-context** — making a 5-axis matrix. Repo-contexts have task-affinity tags
to avoid nonsensical combinations.

### 2. Add repo-context axis

#### 2a. Create `repo_contexts/` directory structure

Same layout as `methodologies/`:

```
repo_contexts/
  none/
    manifest.yaml          # noop: true (no context)
  pyvrp-instructions/
    manifest.yaml
    content/
      CLAUDE.md            # PyVRP-specific instructions
```

The `none` repo-context is the baseline (like `baseline` for methodologies).

#### 2b. Manifest format — add `task_affinity`

Extend the existing `Manifest` model in `core/manifest.py` to support an optional
`task_affinity` field:

```python
@dataclass
class Manifest:
    id: str
    description: str
    source: Source | None = None
    noop: bool = False
    task_affinity: list[str] = field(default_factory=list)
    harnesses: dict[str, list[FileMapping]] = field(default_factory=dict)
```

`task_affinity` is a list of task IDs this context applies to. **Empty list means
"applies to all tasks"** (the default). This field is used by repo-contexts but
ignored for methodologies.

#### 2c. Create `core/repo_context_loader.py`

Mirror `core/methodology_loader.py` (née `setup_loader.py`):

```python
def load_repo_context(context_id: str, harness: str) -> RepoContextSpec: ...
def list_repo_contexts() -> list[str]: ...
def get_task_affinity(context_id: str) -> list[str]: ...
```

`RepoContextSpec` is identical in shape to `MethodologySpec` — it has an `id` and
`files: dict[str, list[str]]`. Add it to `core/models.py`:

```python
@dataclass
class RepoContextSpec:
    id: str
    files: dict[str, list[str]]
```

#### 2d. Extend `Trial` model

Add `repo_context_id` field to `Trial`:

```python
@dataclass
class Trial:
    id: str
    task_id: str
    methodology_id: str       # was setup_id
    repo_context_id: str      # NEW — "none" for no context
    model: str
    runner: str
    rep: int
```

Update the trial ID format:
`{task}_{methodology}_{repo_context}_{model}_{runner}_{rep}`

#### 2e. Update DB schema in `core/db.py`

Add `methodology_spec` table (renamed from `setup_spec`), `repo_context_spec`
table, and update `trial` table:

```sql
CREATE TABLE IF NOT EXISTS methodology_spec (
    id TEXT PRIMARY KEY,
    files TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS repo_context_spec (
    id TEXT PRIMARY KEY,
    files TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS trial (
    id TEXT PRIMARY KEY,
    task_id TEXT NOT NULL,
    methodology_id TEXT NOT NULL,
    repo_context_id TEXT NOT NULL,
    model TEXT NOT NULL,
    runner TEXT NOT NULL,
    rep INTEGER NOT NULL
);
```

Add CRUD functions for `repo_context_spec`. Update all trial-related queries.

**Migration note:** Existing `results.db` files have the old schema. Since this
is pre-v1 with no critical data, the prompt should document that old databases
are incompatible and should be deleted or migrated manually. Add a note to the
README about this.

### 3. Update matrix expansion — `core/matrix.py`

`expand()` gets a new `repo_contexts` parameter and affinity filtering:

```python
def expand(
    tasks: list[str],
    methodologies: list[str],
    repo_contexts: list[str],
    models: list[str],
    runner: str,
    reps: int,
    full_matrix: bool = False,
) -> list[Trial]:
```

Logic:
1. Validate methodologies against harness (existing behavior, renamed)
2. Validate repo-contexts against harness (same pattern)
3. For each `(task, methodology, repo_context, model, rep)`:
   - If not `full_matrix`, check repo-context's `task_affinity`:
     if affinity list is non-empty and task_id not in it, skip
   - Otherwise, include in trial list

### 4. Update executor — `core/executor.py`

In `execute_trial()`, apply files in this order:
1. **Repo-context files** — the fixed environment (applied first)
2. **Methodology files** — the thing under test (applied on top)

Both use the same `lay_down_setup_files()` mechanism from `runners/base.py`
(rename to `lay_down_files()` for generality). The repo-context commit message
should be `"setup-bench: lay down repo context files"` and the methodology commit
message stays `"setup-bench: lay down methodology files"` (update from current
`"setup-bench: lay down setup files"`).

Load both specs:
```python
methodology = load_methodology(trial.methodology_id, harness)
repo_context = load_repo_context(trial.repo_context_id, harness)
```

## What NOT to do

- Don't change the manifest file format beyond adding `task_affinity` — the
  existing `harnesses` / `FileMapping` structure works for both axes.
- Don't implement Methodology × Repo-Context composition merging — they're
  applied sequentially (context first, methodology second), not merged.
- Don't worry about backward compatibility with old `results.db` — document the
  break and move on.
